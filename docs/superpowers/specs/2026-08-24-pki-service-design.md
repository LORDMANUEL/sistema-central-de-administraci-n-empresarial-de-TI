# IT Guardian PKI Service Design

**Version target:** v0.4.0 — PKI first, Enrollment second  
**Date:** 2026-08-24  
**Status:** approved platform architecture, implementation gate for `pki-service`

## Goal

Build an independently deployable PKI microservice that issues, inventories, rotates and revokes device certificates without ever receiving a device private key. It becomes the certificate authority boundary used by Enrollment, Gateway and later Guardian agents.

## Service boundary

`pki-service` owns:

- online intermediate CA material;
- device certificate issuance records;
- certificate serial/fingerprint/status/lifetime;
- revocation state and CRL generation;
- issuance idempotency;
- PKI audit-domain events through transactional outbox;
- validation of short-lived Enrollment issuance grants;
- tenant-scoped administrative certificate inventory/revocation.

It does **not** own users, tenants, assets, enrollment tokens, agent commands, telemetry or device private keys.

Databases remain isolated: `guardian_pki` is written only by `pki-service`.

## CA hierarchy

The initial self-hosted hierarchy is:

```text
Guardian Root CA (RSA 4096, long-lived)
        │
        └── Guardian Device Intermediate CA (RSA 3072, online signer)
                  │
                  ├── Device certificate A
                  ├── Device certificate B
                  └── Device certificate N
```

`pki-ca-init` initializes the hierarchy idempotently. The root private key is stored in a dedicated Docker volume mounted only into the init job. Runtime `pki-service` mounts only the online intermediate key/certificate plus root certificate needed to return the chain.

This is an RC bootstrap design. Enterprise Stable must support moving the signer to OpenBao/HSM-compatible custody without changing the public PKI API.

## Key ownership

Device private keys are generated by the device/agent. Enrollment submits a PKCS#10 CSR. PKI validates the CSR and signs only the public key.

Supported initial CSR keys:

- RSA >= 2048 bits;
- EC P-256 (`secp256r1`);
- EC P-384 (`secp384r1`).

RSA remains available for legacy Windows/macOS compatibility. Unsupported/weak keys are rejected before issuance.

## Device identity

Every certificate is bound to:

- `tenant_id`;
- `guardian_asset_id`;
- `device_id`;
- `platform`;
- unique `issuance_id`.

The canonical SAN URI is:

```text
spiffe://guardian/tenant/<tenant_id>/asset/<guardian_asset_id>/device/<device_id>
```

The certificate CN is a short non-secret device label; authorization must use SAN identity/Guardian IDs, never CN alone.

## Certificate profile

Default device lifetime: 30 days. Configurable production range: 1–90 days.

Certificate extensions:

- BasicConstraints CA=false;
- KeyUsage digitalSignature plus keyEncipherment for RSA;
- ExtendedKeyUsage CLIENT_AUTH;
- SubjectAlternativeName with canonical Guardian URI;
- AuthorityKeyIdentifier;
- SubjectKeyIdentifier.

The service never backdates excessively: a small configurable clock-skew allowance is used for `not_before`.

## Enrollment issuance grant

Device issuance is not authorized by a shared API secret. Enrollment Service will sign a short-lived Ed25519 JWT grant and publish its public key via JWKS.

Required claims:

- `iss = urn:it-guardian:enrollment`;
- `aud = it-guardian-pki`;
- `type = certificate_issue` or `certificate_rotate`;
- `sub = device_id`;
- `tenant_id`;
- `asset_id`;
- `device_id`;
- `issuance_id`;
- `csr_sha256`;
- `iat`, `exp`, `jti`;
- signing `kid`.

Grant lifetime must not exceed 120 seconds. PKI compares every bound claim with the request and CSR fingerprint before signing.

## Administrative authorization

Management APIs validate Identity Ed25519 access JWTs using Identity JWKS.

- `platform_admin`: global certificate read/revoke.
- `org_admin`: certificate read/revoke for active tenant memberships resolved through Tenant Service.
- other tenant roles: no PKI management access.
- suspended tenant: tenant-scoped management denied.

No PKI service reads Identity or Tenant database tables.

## API v1

Public/bootstrap endpoints:

- `GET /health/live`
- `GET /health/ready`
- `GET /metrics`
- `GET /api/v1/ca/chain`
- `GET /api/v1/ca/crl`

Enrollment-authenticated endpoints:

- `POST /api/v1/certificates/issue`
- `POST /api/v1/certificates/rotate`

Administrative endpoints:

- `GET /api/v1/certificates?tenant_id=...`
- `GET /api/v1/certificates/{certificate_id}`
- `POST /api/v1/certificates/{certificate_id}/revoke`

## Idempotency

`issuance_id` is globally unique in PKI.

- first valid request creates and signs a certificate;
- identical retry with the same `issuance_id`, CSR fingerprint and identity returns the existing certificate;
- same `issuance_id` with different bound data returns `409 pki.issuance_conflict`;
- rotation has a new `issuance_id` and references the certificate being replaced.

This prevents duplicate certificates when Enrollment retries after network uncertainty.

## Revocation and CRL

Revocation is persistent and idempotent. Supported reasons include `key_compromise`, `cessation_of_operation`, `superseded`, `affiliation_changed`, `privilege_withdrawn` and `unspecified`.

`GET /api/v1/ca/crl` builds a signed CRL from revoked certificates with `last_update`, `next_update` and CRL number. Later Gateway/OCSP work can add real-time status without changing revocation storage.

## Rotation

`certificate_rotate` issuance requires:

- valid Enrollment grant;
- existing active certificate for the same tenant/asset/device;
- new CSR/private key;
- new `issuance_id`.

PKI issues the replacement first, then marks the previous certificate revoked with reason `superseded` in the same domain operation. Automatic endpoint renewal will be wired through Gateway/Agent Control later; PKI provides the safe primitive now.

## Persistence

`certificates`:

- `id` UUID;
- `issuance_id` UUID unique;
- `tenant_id`, `asset_id`, `device_id`;
- `platform`;
- `serial_hex` unique;
- `csr_sha256`;
- `fingerprint_sha256` unique;
- `subject_cn`, `san_uri`;
- `certificate_pem`;
- `not_before`, `not_after`, `issued_at`;
- `status` active/revoked;
- `replaces_certificate_id` nullable;
- `revoked_at`, `revocation_reason` nullable.

`outbox_events` follows the existing versioned Guardian envelope and resilient delivery fields (`attempts`, `last_error`, `published_at`).

## Events

- `pki.certificate.issued`;
- `pki.certificate.rotated`;
- `pki.certificate.revoked`.

Envelope is `schema_version=1`, with `event_id`, `type`, aggregate identity, occurrence time and `data`.

## Error contract

Stable Guardian envelope with request ID. Initial domain codes include:

- `pki.ca_unavailable`;
- `pki.invalid_csr`;
- `pki.weak_key`;
- `pki.invalid_grant`;
- `pki.grant_expired`;
- `pki.grant_binding_mismatch`;
- `pki.issuance_conflict`;
- `pki.certificate_not_found`;
- `pki.certificate_revoked`;
- `pki.rotation_identity_mismatch`;
- `pki.access_denied`;
- `pki.org_admin_required`;
- `pki.tenant_suspended`.

## Observability

- `/health/live`: process health only;
- `/health/ready`: database + parsable intermediate signer material;
- Prometheus HTTP counters plus issuance/revocation/outbox counters;
- structured JSON request logs with `request_id`;
- no CSR private material, bearer token or PEM private key in logs.

## Docker and installation

Compose adds:

- `pki-db-init`;
- `pki-ca-init`;
- `pki-migrate`;
- `pki-service`;
- `pki-outbox-worker`;
- volumes `guardian-pki-root` and `guardian-pki-online`.

Runtime service is non-root. Root private material is not mounted into the API/worker containers.

## Security invariants

1. Device private key never traverses Guardian APIs.
2. Root private key is unavailable to runtime API containers.
3. Issuance requires a short-lived cryptographically verified grant bound to CSR and device identity.
4. Management requires Identity + Tenant authorization.
5. Weak/invalid CSRs are rejected before any DB issuance record is committed.
6. Certificate issuance is idempotent by `issuance_id`.
7. Revocation survives restart and appears in signed CRL.
8. No other service writes `guardian_pki` tables.
9. Signing key paths/material are never returned by API or logs.
10. NATS outage cannot lose PKI domain events.

## Test gate

The service is not DONE until all are green:

- CA hierarchy generation/idempotence;
- signer readiness;
- RSA/EC CSR validation and weak-key rejection;
- issuance grant cryptographic validation/binding/expiry;
- certificate profile/SAN/chain verification;
- issuance idempotency/conflict;
- tenant-scoped management authorization;
- revocation and CRL membership;
- rotation + superseded revocation;
- transactional outbox resilience;
- Alembic upgrade/downgrade/upgrade;
- non-root Docker build;
- Compose validation;
- clean PKI stack smoke test.

Only after this gate closes does v0.4 proceed to `enrollment-service`.
