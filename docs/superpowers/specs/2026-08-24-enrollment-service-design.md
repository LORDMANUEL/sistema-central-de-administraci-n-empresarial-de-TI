# IT Guardian Enrollment Service Design

**Version target:** v0.4.0 — Enrollment after certified PKI  
**Date:** 2026-08-24  
**Status:** approved continuation of the Core MVP roadmap

## Goal

Build an independently deployable Enrollment microservice that lets an administrator generate a short-lived, high-entropy one-time enrollment token bound to an existing Guardian asset. An endpoint redeems that token with a CSR, receives a certificate from PKI without ever sending its private key to Guardian, and becomes a stable Guardian device identity.

The complete successful path is:

```text
Identity admin token
      |
      v
Enrollment Token create
      |
      +--> Tenant Service authorization
      +--> Asset Service validation
      |
      v
one-time token plaintext returned once
      |
      v
Endpoint generates private key + CSR
      |
      v
POST /api/v1/enrollments
      |
      v
Enrollment reserves token + creates stable device_id
      |
      v
Enrollment signs <=120s PKI grant
      |
      v
PKI issues client certificate
      |
      v
Enrollment marks token consumed + device enrolled
      |
      v
device.enrolled -> transactional outbox -> NATS JetStream
```

## Service boundary

`enrollment-service` owns:

- enrollment token lifecycle;
- token hashing and one-time/replay semantics;
- device enrollment state;
- stable `device_id` generation;
- Enrollment Ed25519 signing material used only for PKI grants;
- public Enrollment JWKS;
- orchestration of the PKI issuance call;
- enrollment-domain transactional outbox events.

It does **not** own:

- users or passwords;
- tenant/site/department data;
- canonical assets;
- CA keys or certificate signing;
- endpoint private keys;
- agent commands, telemetry or inventory.

`guardian_enrollment` is written only by Enrollment Service.

## Trust boundaries

### Administrator path

Administrators authenticate with an Identity access token. Enrollment validates the Identity JWT using Identity JWKS and resolves tenant authorization through Tenant Service.

- `platform_admin`: global token management.
- `org_admin`: token management for active tenants they administer.
- viewer/other membership: denied.
- suspended tenant: denied.

The same administrator bearer token is forwarded to Asset Service when validating the asset during token creation. Enrollment never reads Tenant or Asset databases directly.

### Endpoint path

The endpoint has no Identity account before enrollment. It authenticates with the high-entropy enrollment token only.

The endpoint never receives:

- Enrollment private signing key;
- PKI intermediate/root private key;
- another device's enrollment state.

The endpoint private key is generated locally and only the CSR reaches Guardian.

## Enrollment token

### Token generation

Plaintext token format:

```text
gdt_<urlsafe-random-43+ chars>
```

The random payload has at least 256 bits of entropy generated with `secrets.token_urlsafe(32)`.

### Token persistence

Plaintext is never stored. Enrollment stores:

- `token_hash = SHA256(plaintext_token)`;
- optional non-secret `token_hint` consisting only of a short prefix/suffix for administrative identification;
- tenant/asset binding;
- creator user ID;
- expiry;
- reservation/consumption state.

SHA-256 is acceptable because tokens are generated by the server with >=256 bits of entropy; this is not password hashing.

### Lifetime

Default lifetime: 60 minutes. Configurable range: 5 minutes to 24 hours.

Expired or revoked tokens cannot begin a new enrollment.

### One-time and retry semantics

The token is logically one-time, but network retries must be safe.

A token therefore transitions:

```text
ACTIVE -> RESERVED -> CONSUMED
          |
          +-> ACTIVE again only after deterministic pre-certificate failure
```

Rules:

1. First valid redemption atomically reserves the token for one `DeviceEnrollment` and one request fingerprint.
2. Concurrent redemption with different request data is rejected with `enrollment.token_replay`.
3. Identical retry while RESERVED resumes the same `device_id` and `issuance_id`.
4. After CONSUMED, identical retry returns the already-issued enrollment result.
5. After CONSUMED, mismatched reuse is rejected as replay.
6. Network/PKI 5xx uncertainty leaves reservation bound to the same enrollment so a retry reuses the same PKI `issuance_id`.
7. Deterministic pre-certificate failures may release reservation so the same token can be retried after fixing a malformed CSR/request, provided no certificate was issued.

This distinguishes operational retry from malicious replay.

## Request fingerprint

The reservation is bound to a deterministic SHA-256 over canonical enrollment inputs:

- token-bound `tenant_id`;
- token-bound `asset_id`;
- CSR DER SHA-256;
- normalized platform;
- normalized hostname;
- agent version when supplied.

The plaintext token itself is not included in logs or events.

## Device identity

Enrollment generates a server-side UUIDv4 `device_id` when a token is first reserved.

The device is permanently bound to:

- `tenant_id`;
- `guardian_asset_id` (`asset_id`);
- `device_id`;
- `platform`;
- initial CSR hash;
- certificate ID/serial returned by PKI.

One asset may later support multiple device identities only through explicit product requirements; v0.4 defaults to one active initial enrollment per token and does not infer hardware identity from hostname.

## CSR policy

Enrollment performs lightweight validation before reserving a token:

- valid PEM PKCS#10;
- CSR signature valid;
- public key type RSA or EC;
- RSA >=2048;
- EC P-256/P-384.

This mirrors the current PKI acceptance profile so malformed requests do not unnecessarily reserve tokens. PKI remains authoritative and re-validates every CSR.

Enrollment never imports PKI database state or signing code.

## PKI grant signer

Enrollment has its own Ed25519 signing key and JWKS endpoint:

```text
GET /.well-known/jwks.json
```

Configuration:

- `ENROLLMENT_SIGNING_KEY`: base64url-encoded 32-byte Ed25519 seed;
- `ENROLLMENT_JWT_KEY_ID`: default `enrollment-ed25519-v1`;
- issuer: `urn:it-guardian:enrollment`;
- audience: `it-guardian-pki`.

Production rejects an absent/invalid signing seed.

Required PKI grant claims:

- `iss`;
- `aud`;
- `type = certificate_issue`;
- `sub = device_id`;
- `tenant_id`;
- `asset_id`;
- `device_id`;
- `issuance_id`;
- `csr_sha256`;
- `iat`;
- `exp`;
- `jti`;
- header `kid`.

Grant lifetime defaults to 60 seconds and must not exceed the PKI 120-second policy.

The grant is server-to-server only and is never returned to the endpoint.

## PKI orchestration

Enrollment calls:

```text
POST /api/v1/certificates/issue
Authorization: Bearer <short-lived enrollment grant>
```

Request uses the stable `issuance_id` persisted in `DeviceEnrollment`.

Retry behavior:

- connection timeout/5xx: retry with the same `issuance_id` and same CSR identity;
- 200 from PKI means an idempotent retry returned the existing certificate;
- 201 means newly issued;
- 409 issuance conflict is a domain failure and must never be hidden by creating a new issuance ID;
- 4xx CSR/grant failures are deterministic and reported using stable Enrollment error codes.

Enrollment stores the public certificate result required to answer future identical retries:

- PKI `certificate_id`;
- serial;
- fingerprint;
- PEM certificate;
- CA chain;
- not_before/not_after.

No private material is stored.

## Data model

### `enrollment_tokens`

- `id` UUID primary key;
- `token_hash` SHA-256 hex, unique/indexed;
- `token_hint` non-secret display hint;
- `tenant_id`;
- `asset_id`;
- `created_by_user_id`;
- `created_at`;
- `expires_at`;
- `revoked_at` nullable;
- `reserved_at` nullable;
- `reserved_enrollment_id` nullable;
- `consumed_at` nullable;
- `consumed_device_id` nullable.

### `device_enrollments`

- `id` UUID primary key;
- `device_id` UUID unique/indexed;
- `token_id` unique for v0.4 one-token/one-enrollment;
- `tenant_id`;
- `asset_id`;
- `platform`;
- `hostname`;
- `agent_version` nullable;
- `csr_sha256`;
- `request_fingerprint`;

Uses the existing Guardian outbox schema:

- payload;

## API v1

### Administrative

```text
POST /api/v1/enrollment-tokens
GET  /api/v1/enrollment-tokens?tenant_id=...
POST /api/v1/enrollment-tokens/{token_id}/revoke
GET  /api/v1/enrollments?tenant_id=...
GET  /api/v1/enrollments/{device_id}
```

Token create request:

```json
{
  "tenant_id": "uuid",
  "asset_id": "guardian-asset-id",
  "expires_in_minutes": 60
}
```

Create response returns plaintext `token` **only once** together with non-secret metadata.

List/get responses never expose token hash or plaintext.

### Endpoint enrollment

```text
POST /api/v1/enrollments
```

Request:

```json
{
  "token": "gdt_...",
  "platform": "windows",
  "hostname": "WS-SPS-001",
  "agent_version": "0.7.0-dev.1",
  "csr_pem": "..."
}
```

Success response:

```json
{
  "status": "enrolled",
  "device_id": "uuid",
  "tenant_id": "uuid",
  "asset_id": "guardian-asset-id",
  "certificate_id": "uuid",
  "certificate_pem": "...",
  "ca_chain_pem": "...",
  "not_before": "ISO-8601",
  "not_after": "ISO-8601"
}
```

No Identity bearer token is required for this endpoint.

## Asset validation

When an administrator creates an enrollment token, Enrollment calls Asset Service using the administrator's bearer token:

```text
GET /api/v1/assets/{asset_id}
```

The returned asset must have `tenant_id == requested tenant_id`.

Errors:

- 404 -> `enrollment.asset_not_found`;
- tenant mismatch -> `enrollment.asset_tenant_mismatch`;
- 403 -> `enrollment.access_denied`;
- Asset 5xx/network -> `enrollment.asset_service_unavailable`.

This validation happens before token persistence.

## State machine

```text
Token ACTIVE
   |
   | valid endpoint request
   v
Token RESERVED + Enrollment PENDING
   |
   | PKI certificate success
   v
Enrollment CERTIFICATE_ISSUED
   |
   | same DB transaction finalization
   v
Enrollment ENROLLED + Token CONSUMED + device.enrolled outbox
```

For v0.4, `CERTIFICATE_ISSUED` may be a transient persisted recovery state used if certificate response is stored before final event transaction; normal successful request should end at ENROLLED.

## Failure handling

### Before reservation

Malformed token, expired token, revoked token, malformed CSR, invalid platform/hostname do not mutate the database.

### While reserved

Network/PKI 5xx:

- keep enrollment PENDING;
- keep token RESERVED;
- persist a non-secret failure code/message;
- identical retry resumes.

Deterministic PKI 4xx before certificate issuance:

- mark attempt FAILED for audit;
- release token reservation if no certificate exists;
- emit `device.enrollment.failed`;
- token remains usable until expiry/revoke.

### After certificate issuance

Once a PKI certificate exists, Enrollment must never create a new issuance ID to recover. It either finalizes the same enrollment or retrieves the same certificate idempotently from PKI.

## Events

- `enrollment.token.created`;
- `enrollment.token.revoked`;
- `device.enrolled`;
- `device.enrollment.failed`.

Events never contain:

- plaintext enrollment token;
- token hash;
- bearer token;
- CSR PEM;
- Enrollment signing seed;
- certificate private key.

`device.enrolled` includes only non-secret identity/certificate metadata.

## Observability

Endpoints:

- `GET /health/live`;
- `GET /health/ready`;
- `GET /metrics`.

Readiness requires:

- database connectivity;
- valid Enrollment Ed25519 signer configuration;
- no synchronous dependency on PKI/Asset/Tenant availability so temporary downstream failure does not make the process itself unready.

Metrics:

- HTTP requests;
- enrollment tokens created/revoked;
- enrollment successes/failures;
- PKI request attempts/success/failure;
- outbox published/failed.

Logs contain method, route template, status, request ID and duration only. They never log Authorization, request body, plaintext token or CSR.

## Docker and installation

Compose adds:

- `enrollment-db-init`;
- `enrollment-migrate`;
- `enrollment-service`;
- `enrollment-outbox-worker`.

Database: `guardian_enrollment`.

Backend port during pre-Gateway development: loopback `127.0.0.1:8005`.

Runtime containers run as non-root.

Enrollment signing seed is passed only to `enrollment-service`; the outbox worker does not need and must not receive the private signer seed.

PKI receives only Enrollment JWKS over HTTP, never the seed.

## Security invariants

1. Plaintext enrollment tokens are returned once and never persisted.
2. Tokens use >=256 bits server-generated entropy.
3. Endpoint private keys never traverse Enrollment or PKI APIs.
4. Enrollment signing seed never leaves Enrollment API runtime.
5. PKI receives only signed short-lived grants/JWKS public material.
6. Asset/Tenant/Identity databases are never read directly by Enrollment.
7. One-time token race is protected by DB row locking/unique constraints.
8. Identical retry is idempotent; mismatched reuse is replay and is denied.
9. A network retry never generates a new PKI issuance ID.
10. Secrets, token values, hashes and CSR bodies never appear in logs/events.
11. Successful enrollment and `device.enrolled` event are committed transactionally.
12. NATS outage cannot lose enrollment domain events.

## Certification gate

Enrollment is not DONE until the same candidate SHA passes:

- token entropy/hash/plaintext-once tests;
- Identity/Tenant admin authorization tests;
- Asset API validation tests;
- expired/revoked token tests;
- concurrent one-time reservation test;
- identical retry tests for RESERVED and CONSUMED states;
- mismatched replay rejection tests;
- CSR/key policy tests;
- Enrollment Ed25519 JWKS/grant tests;
- PKI retry/idempotency tests;
- success finalization and outbox tests;
- deterministic failure release tests;
- transient failure reservation tests;
- secret-safe logs/events tests;
- Alembic upgrade/downgrade/upgrade;
- Docker non-root build;
- Compose validation;
- clean-stack E2E `Identity -> Tenant -> Asset -> Enrollment -> PKI -> certificate -> JetStream`;
- clean-stack replay/retry assertions;
- verification that PKI runtime cannot access Enrollment private signing seed;
- full teardown from empty volumes.

Only after this gate passes can v0.4.0 be promoted and v0.5 Gateway/Audit begin.
